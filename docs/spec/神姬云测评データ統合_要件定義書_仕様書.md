## 0. サマリー

現行の `kamihimeProject` は docsify ベースの静的Wikiで、属性別ページ（`hime/fire.md` など）にキャラごとの**一言評価＋画像**のみを掲載する「簡評」形式になっている。

新しく取り込む `神姬云测评-翻译版.xls` は、属性ごとのシートに約177体のキャラクター、10体の英霊、真化・覚醒フォーム、武器効果量早見表を含む、**スキル全文＋数値＋攻略コメントの詳細データ**（簡体字中国語）である。

v2ではレビューで得た回答に基づき決定1〜7を確定したが、実装・目視レビューを経て**v3で決定3・決定7を以下のとおり変更**した（火属性で実装・反映済み）。

| # | 論点 | 結論 |
|---|---|---|
| 1 | 著作権表記 | **作成者名・QQ群番号は一切掲載しない。**「神姬云测评（翻訳版）」というデータソース名と更新日のみ記載 |
| 2 | 総評文の言語 | **中国語原文＋日本語訳を併記**する |

## 1. 背景・目的

### 1.1 背景
- 現行サイトの「簡評」は導入向けとしては機能しているが、スキル詳細・数値・CD等の一次情報が無く、実戦での判断材料としては不十分。
- `神姬云测评` は中国語圏コミュニティが公開しているキャラ評価表で、シーズンごとに更新されている一次情報源。今回のバージョンは2026-07-16更新。

### 1.2 目的
1. xls内の評価・スキルデータを、日本語話者の閲覧者にも読める形（中日併記）でサイトに掲載する。
2. **簡評ページの雰囲気・編集資産を一切壊さずに**、詳細データを同一ページ内に追加する（既存の簡評文は`<details>`で折りたたみ・保存）。
3. xlsが今後もバージョンアップされることを前提に、次回以降の取り込み作業を再現可能な手順（変換スクリプト）にする。

### 1.3 スコープ外（今回やらないこと）
- xlsファイル自体の配布・埋め込み（今回転記するのは翻訳・整形した内容であり、元ファイルはサイトに置かない）。
- ゲーム内画像・アイコンの新規収集（既存 `hime/images` にないキャラの画像は別途手配）。
- 検索基盤の刷新（既存の `js/search.js` をそのまま使う）。

### 3.2 レコード構造（属性シート・英霊シート共通パターン）
1キャラ＝可変長の複数行ブロック。パースには以下の状態遷移が必要。

```
[空行]
［限定名］キャラ名                          ← ブロック開始（列A、単独）
（任意）自由記述の総評コメント（列B、1〜数百字、By 執筆者名を含むことがある）
技能详细 | 持续 | CD                         ← テーブルヘッダ行（固定）
B特效    | （常時発動効果の説明）
■技能1   | 説明文（\n区切りで複数段落） | 持続 | CD
■技能2   | ...
■技能3   | ...
■技能4 / ■EX | ...（キャラにより有無・数が異なる）
被动1    | 説明文 | （持続/CDが入る場合あり）
被动2    | ...
（英霊のみ）专武效果 セクション：B特效／属性別専用武器の強化内容
[空行] → 次のキャラへ
```

- 実質使用列は **A列（見出し/技能名）・B列（本文）・C列（持続）・D列（CD）** の4列のみ。
- 総評コメント行は**存在しないキャラもある**（新規追加直後で評価未執筆、等）。パーサは無くても落ちない前提。
- キャラ名は `［入手経路・限定名］本名` の形式（例: `［真夏の恋心］TG-99`）。
- 総評コメントの末尾に `——By 執筆者名` が含まれることがある → **決定1により、この署名部分は転記時に必ず削除する。**

### 3.3 `真化·觉醒`（真化・覚醒）シート
属性シートと同一のブロック構造。追加情報として「真化に必要な素材と強化数値の合計」の行を含む。**決定4により**、対応する通常フォームへの統合は行わず、詳細ページ上で見出しを分けた独立エントリとして掲載する（例: `### フルーレティ` の直後に `### フルーレティ［神想真化］` を別見出しとして並べる）。

属性の判定: このシート自体には属性列が無いため、以下の優先順で決定する。
1. 技能本文中の属性キャラ参照（例:「水属性角色」「火属性角色」）から推定。
2. 判定できない場合は、同名の通常フォームが既に存在する属性ページに合わせる。
3. どちらでも判定不能な場合は変換スクリプトが「要確認リスト」に出力し、自動配置しない。

### 3.4 `英灵`（英霊）シート
属性シートとほぼ同一構造だが、末尾に **专武效果（専用武器効果）** セクションを持つ。英霊は属性を持たないため独立ページ（`hime/spirits.md`）として扱う（決定5）。

### 3.5 `武器效果量`（武器効果量早見表）シート
キャラ/英霊データとは別形式（2カラム×2セットの横並び表、B〜Qの17列）。静的な参照テーブルとしてそのままMarkdownテーブル化する。

### 3.6 データ品質・パース上の注意点
- 中国語（簡体字）本文中に日本語の原語技能名・キャラ名がそのまま埋め込まれている箇所が多い（例:「获得【福音】」）。**決定2により、中国語原文はそのまま残し、その下に日本語訳を追加する**（原語の固有名詞・システム名はカタカナ／原表記のまま訳文に残す）。
- 表記ゆれ: 総評コメントの有無で行位置がずれるため、「次の行が `技能详细` ヘッダかどうか」で判定するロジックが必須（実装済み・動作確認済み）。
- 一部キャラは技能4が `■EX` 表記（英霊・一部限定キャラ）。
- 更新履歴が本文中に直接埋め込まれている（例: `*2025/11/27 追加ex评价`）。これは総評コメントの一部としてそのまま訳出する（別構造化はしない）。

## 4. 要件定義

### 4.1 利用者像
- **既存想定ユーザー**: 序盤〜中盤のプレイヤーが「このキャラは使えるか」を短時間で把握したい（現行の簡評はこの用途に最適化・維持）。
- **今回追加する想定ユーザー**: 編成を詰めたい中〜上級者が、スキルの発動条件・CD・数値を見て他キャラとの組み合わせを検討したい（新設の詳細ページで対応）。

### 4.2 機能要件

| ID | 要件 | 優先度 |
|---|---|---|
| F-1 | 属性別ページ（`hime/fire.md` 等）**内の技能详细セクション**に、xls由来の全キャラのスキル詳細（技能1〜4・被動・B特効・持続・CD）を**中国語原文＋日本語訳併記**で掲載する（v3：別ページではなく同一ページ内） | 必須 |
| F-2 | 各キャラの総評コメント（xlsにあるもの）を中日併記で掲載する。無いキャラは項目自体を省略する。執筆者署名は削除する | 必須 |
| F-3 | 真化・覚醒フォームは、対応する通常フォームとは別の独立キャラエントリとして技能详细セクションに追記する | 必須 |
| F-4 | 英霊専用の詳細ページ（`hime/spirits.md`）を新規作成し、10体のスキル詳細・専用武器効果を中日併記で掲載する（英霊はキャラ単位の既存簡評が存在しないため独立ページのまま） | 必須 |
| F-5 | 武器効果量早見表を独立ページ（`hime/weaponEffects.md`）として新設する | 必須 |
| F-6 | 既存の簡評ページ（`hime/fire.md`等）の本文は**`<details>`（デフォルト折りたたみ）内に格納するのみで内容は一切改変しない**。技能详细セクションはマーカーコメントで区切り、同一ファイルの下部に追記する（v3） | 必須 |
| F-7 | サイト内検索（`js/search.js`）が新規セクションの本文（キャラ名・技能名・日本語訳）もヒットさせる | 必須 |
| F-8 | サイドバー（`_sidebar.md`）に英霊ページ・武器効果量ページへの導線を追加する（属性別ページは1ページ統合のためリンク追加不要） | 必須 |
| F-9 | 技能详细セクションの冒頭に、データソース名（神姬云测评 翻訳版）と更新日（2026-07-16）のみを明記する。**作成者名・QQ群番号等の個人情報は一切記載しない** | 必須 |
| F-10 | 次回以降のxls更新を取り込む際、手作業を最小化する変換手順（スクリプト）を用意する | 必須 |
| F-11 | 詳細ページの冒頭に「このページは自動生成です。手動編集は次回更新時に失われます」という注記を入れる | 必須 |
| F-12 | 技能テキスト中の独自用語（【欧拉链接】等）の訳語を統一するための**用語対訳表**を用意し、変換スクリプトから参照する | 必須（翻訳品質担保のため優先度を引き上げ） |
| F-13 | キャラ名から詳細ページ内アンカーへ飛べる目次を用意する | 推奨 |
| F-14 | 各キャラの詳細ページにキャラ立ち絵（xls埋め込み画像から抽出）をカード形式で表示する | 必須（2026-08-18追記。ユーザーレビューで「見にくい」と指摘を受け追加） |

### 4.3 非機能要件

| ID | 要件 |
|---|---|
| N-1 | 追加のビルドツールチェーンを導入しない。変換はリポジトリ内スクリプトの一回限りの実行とし、成果物は静的`.md`として配置する |
| N-2 | 既存デザイン（`css/default.css` 等）・カラースキームを踏襲する |
| N-3 | 詳細ページは1属性1ファイル（約25〜33体×中日併記スキル詳細）となり、現行 `fire.md`（14KB）よりかなり大きくなる見込み。閲覧性向上のため、各キャラを `<details>` で折りたたみ、目次（F-13）で直接ジャンプできるようにする |
| N-4 | 変換スクリプトはリポジトリに残し、次回更新時に再実行できること（Node.js、追加npm installなし） |
| N-5 | 詳細ページは完全自動生成物として扱い、通常運用での手編集は行わない（F-11、5.5節） |

### 4.4 情報設計方針（v3で確定・1ページ統合方式）

**簡評と技能详细を同一ファイル（`hime/<属性>.md`）に統合する。ページ分割は行わない。**

```
hime/fire.md
├─ 導入文（既存・手書き、無改変）
├─ <details><summary>旧神姫簡評</summary> … </details>
│    既存の簡評（キャラ見出し＋画像＋一言評価）をそのまま格納。デフォルト折りたたみ（非表示）。
│    手編集エリア。変換スクリプトは書き込まない。
└─ <!-- KAMIHIME:DETAIL:fire:START --> … <!-- KAMIHIME:DETAIL:fire:END -->
     技能详细セクション（中日併記、キャラ立ち絵つき）。完全自動生成・マーカー間のみ差し替え。
```

- 経緯: 初版（v2）では別ページ方式を採用したが、ユーザーレビューで「別ページに分かれていると見にくい／導線が煩雑」との指摘を受け、v3で1ページ統合方式に変更した。
- 旧神姫簡評は「デフォルト非表示（`<details>`は`open`属性なし）」とし、技能详细セクションが常に主表示になるようにする。
- **サイドバーの見出し一覧からも旧神姫簡評を除外する**。`index.html`の`subMaxLevel:4`設定により、docsifyは各ページの`###`見出しを自動でサイドバーのページ内目次に展開するため、`<details>`による本文の折りたたみだけではサイドバーには45件の旧見出しが残ってしまう。旧神姫簡評ブロック内の各`### `見出し行の末尾に、docsify組み込みの`<!-- {docsify-ignore} -->`マーカーを付与し、サイドバー目次からも除外する（技能详细セクション側の見出しには付与しない＝サイドバーに残す）。
- 理由:
  - 1ページで完結し、ページ遷移なしに「概要→詳細」を確認できる。
  - `<details>`は素のHTML機能のため、docsify側の追加実装なしに折りたたみ・デフォルト非表示を実現できる。
  - マーカーコメントで自動生成範囲を明示することで、旧簡評（手編集エリア）を変換スクリプトの誤上書きから守れる（5.5節）。

- **重要な注意（画像タグの書き方）**: 画像は生の`<img src="...">`では**なく**、必ずMarkdown記法`![alt](path)`で書くこと。docsifyは相対パスの自動解決（現在のMarkdownファイルの位置を基準に補正する処理）を`markdown-it`のimageレンダラーにしか適用しない。生HTMLの`<img>`はブラウザがそのまま解釈するため、ハッシュルーティング下では`index.html`のあるサイトルート基準でパスが解決されて壊れる（本プロジェクトで実際に発生し、修正済みの不具合）。

```
        ▼

        ▼

```

決定7（v3）を受けた運用ルール:
- **`hime/<属性>.md` 内の `<!-- KAMIHIME:DETAIL:<属性>:START -->` 〜 `<!-- KAMIHIME:DETAIL:<属性>:END -->` の区間のみが自動生成範囲。** `inject-section.js`はこの区間だけを置き換え、区間外（導入文・`<details>旧神姫簡評</details>`）には一切書き込まない。マーカーが無い場合は末尾に新規追記する。
- **旧神姫簡評（`<details>`内）は手編集エリア。** 直接`hime/<属性>.md`を編集してよい（変換スクリプトが触れない範囲のため安全）。
- `hime/spirits.md`・`hime/weaponEffects.md`は独立ページのまま（キャラ単位で分割された既存簡評が存在しないため、統合の必要がなく元のv2方針を維持）。全体を自動生成物として扱う。
- (1)(4)(5)はNode.js＋同梱`node_modules/xlsx`のみで完結。(3)はPython＋`olefile`（要:ユーザーローカルへの追加インストール、進捗状況確認書2.3節参照）。
- (2)の翻訳は初回は人手（レビュー付き）で`translations.<属性>.json`の`rowsJa`/`summaryJa`を埋め、以降のxls更新では**差分のあった`zh`フィールドのみ再翻訳**すればよい（`characters.<属性>.raw.json`を保持することで差分検出が可能）。

### 5.7 命名・スラグ規則

- 詳細ページの見出しは簡評ページと**同じキャラ名文字列**を使う（`### 妲己觉醒` など）。リンクによる相互参照をアンカー一致で機能させるため。
- 見出しが完全一致しない場合（簡評側での表記ゆれ、簡評に未掲載のキャラ等）は、変換スクリプトが「要確認リスト」に出力する（自動で無理に紐付けない）。
- 真化・覚醒フォームは決定4により独立エントリのため、命名衝突の心配は無い（例: `妲己` と `妲己［神想真化］` は別見出し）。

### 5.8 サイト内検索・ナビゲーション

- `js/search.js` は本文全体を対象にしている前提のため、`hime/<属性>.md`内に統合した技能详细本文（日本語訳含む）も追加対応なくヒットする想定。実装後に目視確認する。ただし`<details>`で折りたたまれた旧簡評・技能详细本文がDOM上に存在すること（`display:none`ではなく単に非表示）が前提のため、docsifyの検索実装がDOM走査型であれば問題ない。
- `_sidebar.md` はv3では属性別ページの追加行は不要（1ページ統合のため）。英霊・武器のみ追加する:
  ```markdown
  - **武器**
    - [词条详解](/hime/arms.md)
    - [效果量表](/hime/weaponEffects.md)
  ```

## 7. リスク

| リスク | 内容 | 対応方針 |
|---|---|---|
| 翻訳品質・一貫性 | 177体超のスキル文を訳すため、同一用語の訳語がページ間でぶれる可能性 | 5.6の用語対訳表を必須参照にし（F-12）、Phase1で運用を確立してからPhase2以降に展開する |
| データ鮮度 | xlsが今後改版されるたびに再変換が必要 | 5.5のパイプラインで再実行コストを最小化。中間JSONにより差分翻訳のみで済む |
| ページ量 | 1ページが1属性あたり数十体分の技能详细を含み縦に長大化 | 旧簡評は`<details>`でデフォルト折りたたみ、各キャラの技能详细も`<details>`で個別折りたたみ＋目次（F-13）で対応。N-3参照 |
| 簡評との内容重複 | 簡評（既存・折りたたみ内）と技能详细セクションの評価内容が食い違う可能性 | 同一ページ内だが表示領域が分離（片方は折りたたみ）しているため実害は小さい。将来的に食い違いが目立てば旧簡評側を手動更新すればよい（技能详细セクションは自動生成のまま） |
| 誤訳の指摘経路 | 自動生成セクションは直接編集禁止のため、誤訳修正の受け皿が必要 | セクション冒頭に「誤訳はIssueで報告」の導線を明記（5.2） |
| マーカー破損 | `hime/<属性>.md`を人手で編集した際に`<!-- KAMIHIME:DETAIL:*:START/END -->`マーカーを誤って削除・改変すると、次回`inject-section.js`実行時にファイル末尾へ重複追記される | `inject-section.js`はマーカーが片方しか見つからない場合はエラーで停止する（5.5節実装済み）。両方消えた場合は末尾追記になるため、コミット前のdiffレビューで検知する |
