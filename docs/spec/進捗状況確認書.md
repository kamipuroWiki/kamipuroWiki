### 2.3 画像抽出の技術メモ（重要・引き継ぎ必須）
- xls（古い.xls=BIFF8/OLE2形式）には埋め込み画像が実在するが、**単純なバイト列コピーでは画像が壊れる**（BIFFレコードの8228バイト境界ごとにCONTINUEレコードのヘッダが挿入され、画像バイナリを分断しているため。実際にCRC検証で破損を確認済み）。
- 対応として `olefile` ライブラリ（本セッションでpipブートストラップ＋`--user --break-system-packages`でインストール）を使い、`scripts/escher.py` でCONTINUEレコードを結合し、MS-ODRAW（Escher）構造を辿って画像を正しく取り出す仕組みを実装した。
- 図形の位置（どの行=どのキャラの画像か）は `FClientAnchor`（レコード種別 `0xF010`。仕様書等でよく見る `0xF00D` は誤りで実際は `ClientTextbox`）から行番号を取得し、`FOPT`内の`pib`プロパティ（`0x0104`）でグローバルな画像ストア（BSE）の何番目かを特定して対応づけている。
- 行番号の昇順（各シート内でのキャラ出現順）とキャラJSONの配列順が一致することを確認済みのため、位置（インデックス）ベースで画像とキャラを対応づけている。
- **環境上の注意**: この環境には`pip`が入っていなかったため、`get-pip.py`をダウンロードして`--user --break-system-packages`でユーザーローカルにpip・olefile・Pillowを導入した（apt/sudoは使用不可のため、この方法以外の選択肢はなかった）。次回別環境で実行する場合は同様の手順が必要になる可能性がある。

### 2.4 不具合修正: 画像が表示されない問題（2026-08-18）
- ユーザーレビューで「追加した画像がうまく表示されない」と報告があり、原因を特定・修正した。
- **原因**: `render-kamihime-md.js`が生の`<img src="images/fire/01.png">`をHTMLとして直接出力していたが、docsifyは相対パスの自動解決（現在のMarkdownファイルの位置を基準に補正する処理）を**Markdown記法`![]()`の画像トークンにしかかけない**（`js/docsify@4.js`のカスタム`image`レンダラー内でのみ実施）。生HTMLの`<img>`はブラウザがそのまま解釈し、ハッシュルーティング下では`index.html`のあるサイトルート基準でパスが解決されるため、実ファイル位置（`hime/detail/images/fire/`）とズレて壊れていた。
- **対応**: `<img>`タグをやめ、`![キャラ名](images/fire/01.png)`のMarkdown記法に変更（docsifyの正規の解決ロジックに乗せる）。`.kh-char`フレックスレイアウトは維持するため、`<div class="kh-char">` → 空行 → `![]()` → 空行 → `<div class="kh-char-body">`という構成にし、CSS側は画像が`<p>`にラップされる分（`.kh-char > p{margin:0;flex:none}`）を追加調整した。
- **未検証事項**: 修正後の見た目は本セッションでは実機ブラウザ確認ができていない（目視確認手段が無い環境のため）。ユーザー側での再確認が必要。

- ユーザーから「sidebarも旧簡評を最初非表示にしたい」との追加要望があった。
- **原因の切り分け**: `<details>`による折りたたみは本文表示のみに効くが、`index.html`の`subMaxLevel: 4`設定により、docsifyは各ページの見出し（`###`など）を自動収集し、左サイドバーの該当リンク（「火系」）の下にページ内目次（サブサイドバー）として展開する仕組みがある（`js/docsify@4.js`の`_renderSidebar`/`subSidebar`実装で確認）。これは本文の折りたたみ状態とは独立して、**Markdown上の見出しをそのまま機械的に列挙する**ため、旧簡評45件の見出しがすべてサイドバーにも表示されてしまっていた。

### 3.3 翻訳作業の実施方法
量が多い（151体＋21体）ため、火属性の翻訳で確立したルール（署名削除、`？`保持、`glossary.json`準拠）を指示書として、水/风/雷/光/暗属性＋真化・覚醒の**6作業を並行するサブエージェントに委任**した。各エージェントは:
- 対象属性の中間JSONを翻訳し、`merge-translations.js`を自分で実行してエラー0件になるまで検証（全6件、初回または数回のやり直しで成功）
- 新規発見した用語を`glossary-additions.<属性>.json`に追加提案（`glossary.json`本体は直接編集させない運用で並行編集の衝突を回避）

全6エージェントの完了後、`glossary-additions.*.json`（計90件、重複除去後71件）を`glossary.json`に統合した（現在163語）。統合時に3件の表記ゆれ（"注目"「タゲ取り」の説明有無、"豆"＝CTか別物か、"监牢"の訳し方）を発見し、内容を確認して1つの表記に統一した（詳細は`glossary.json`の該当エントリのnote参照）。

### 3.4 真化・覚醒フォームの属性判定（決定4の実施結果）
仕様書3.3節の判定手順（①技能テキスト中の属性言及→②同名の通常フォームが存在する属性に合わせる→③判定不能なら要確認）に従って判定した。
